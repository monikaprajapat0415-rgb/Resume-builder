# Prime Resume AI: working agreements

## SEO on every change (standing rule)

Every feature, page or content change must include its SEO work in the same delivery. Do not ship a page without it.
Before calling a change done, go through this list and say in the closing message what was done or why an item does not apply.

1. **Title and description**: unique per page, title under about 60 characters, description under 160. Set in the page's `<SEO />` and in the server-rendered shell if the page has one.
2. **Canonical and robots**: one canonical URL. Filtered, paginated, empty or private views are `noindex, follow`. Private pages (dashboard, admin, forms) use `noindex`.
3. **Server-rendered HTML** for any public page that should rank: add a route in `server/routes/seoRoutes.js` that returns the real h1, copy and links (see `jobSeoController.js`). Unknown or closed items return 404.
4. **Structured data (JSON-LD)**: BreadcrumbList on every page; plus the right type: JobPosting, FAQPage, ItemList, Article, etc. The browser and the server must agree.
5. **Sitemap**: add new public URLs to `getBlogSitemapXml` (database-backed) or `STATIC_ROUTES` (static). Only list pages that have content and are indexable. Never list pending, rejected or hidden items. Imported feed jobs are deliberately NOT in the sitemap (thousands of near-duplicates got the whole site stuck in "Discovered - currently not indexed"); only employer-posted jobs, landing pages, blog and lessons are listed.
6. **nginx**: new public paths must be proxied to Node if they are server-rendered. Check `nginx-blog-snippet.conf` and say if it needs a change.
7. **Internal links**: link new pages from related pages (index, siblings, footer or menu) so crawlers and people can reach them.
8. **Content quality**: real helpful copy, no stuffed keywords, no invented numbers. Write for the audiences we serve: India, UK, Canada and African countries; corporate, factory, skilled trade and daily wage workers.
9. **Test it**: fetch the page without JavaScript and check title, canonical, robots, h1, JSON-LD and sitemap. Then check it in the browser: one title, one canonical, no console errors, no horizontal scroll on a 390px phone.
10. **After deploy**: rebuild the client (`npm run build`), restart pm2, then request indexing of new URL types in Search Console.

## Other rules
- Privacy: never send a job seeker's name, email, phone or user id to employers before the seeker accepts a request.
- Employer jobs and employers need admin approval before they are public.
- Every page except the home page shows a Back button and breadcrumb trail (`client/src/components/PageNav.jsx`, worked out from the URL; mounted in `NavBar`, the app and admin layouts, and `StandalonePageNav` in `App.jsx` for pages with no header). A new route needs a label in `LABELS` if its slug does not read well, and an entry in `LINKABLE` if it is a real parent page. Blog, jobs and learn draw their own trail, so they get the Back button only.
- Career roadmaps (`/roadmaps`, `/roadmaps/:slug`): model `Roadmap`, API `/api/roadmaps`, server-rendered by `roadmapSeoController.js`, in the DB-backed sitemap when published and not noindex, edited at Admin > Career roadmaps. Starter content: `cd server && node scripts/seedRoadmaps.js` (skips existing slugs; `--replace` resets). nginx must proxy `/roadmaps` to Node like `/learn`. The page is a roadmap.sh-style diagram (step boxes on a spine, skills branching off). Signed-in readers get a personal view: `/api/roadmaps/for-me` and `/:slug/for-me` compare their own resumes, CVs and open-to-work profile with each step's skills (`utils/roadmapProfile.js`, word matching, an estimate) and return only derived results, never resume text or anything about other users. Keep steps honest: no invented salaries or promised timelines, and send readers to official sources for licences, tax and legal rules.
- Roadmaps are searchable (`?q=` on `/api/roadmaps` and the search box on `/roadmaps`; `utils/roadmapSearch.js` matches title, aliases, tags and step skills, ignoring spaces and hyphens) and have a `kind`: `career`, `role` (Full Stack Developer, SQL Developer...) or `technology` (React, Docker...). Every step can have a stack `layer` (the "stack end to end" box is built from these at read time) and `resources` (best places to learn: label, https URL, type, free or paid). Role and technology roadmaps are composed from reusable topic modules in `server/scripts/seedTechRoadmaps.js` (skips existing slugs; `--replace` resets). Learning links must be stable official or long-standing sites; run `cd server && node scripts/checkRoadmapLinks.js` on the VPS now and then to find links that moved. Searches and `?kind=` views are `noindex`. No salaries, durations or job-guarantee claims in roadmaps.
- Jobs community (`/jobs/interview-questions` with `/fresher`, `/experienced` and `/:slug`; `/jobs/salaries[/:slug]`; `/jobs/company-reviews[/:slug]`): models `InterviewQuestion`, `InterviewAnswer`, `SalaryReport`, `CompanyReview`; API `/api/community`; admin at Admin > Jobs community (`/api/admin/community`). These fixed paths must stay above `/jobs/:slug` in `seoRoutes.js` and in `App.jsx`, and nginx already proxies `/jobs`. Every reader submission needs login, is rate limited, rejects links, starts as `pending` and shows only after admin approval; 3 different readers flagging an approved item sends it back to pending. Public output shows only `displayName` (first name + last initial, or Anonymous), never user id or email. Pay is never converted between currencies or periods; a range (min/median/max) is shown and indexed only with 3+ approved reports in the same country, currency and period. Company pages are indexed and given `aggregateRating` only with 3+ approved reviews. Starter questions: `cd server && node scripts/seedInterviewQuestions.js`. Interview question model answers must be honest and practical (1 minute read, no invented stats). Filtered or empty views are `noindex`; only pages with content are in the sitemap.
- Menus support one level of sub-menu in the top menu (`MenuItem.parent`; defaults use `parentKey`; Learn and Jobs have dropdowns). `ensureDefaults` only attaches a parent to links it inserts, so existing sites get the new sub-links through Admin > Menus > Restore defaults. Mobile shows sub-links nested; the dropdown opens on hover, focus or tap and closes with Escape. A sub-link can also have an `icon` (a key in `MENU_ICONS`, drawn by `client/src/utils/menuIcons.js`; keep the two lists in sync) and a one-line `description` (90 characters), set in Admin > Menus. The Builder menu (`h-builder` with `h-builder-app` and `h-builder-examples`) and the footer link `fr-examples` reach existing sites through a one-time migration (`migrateBuilder`, marker `migrated-builder-v1`), so nothing needs pressing; the new defaults live in both `server/utils/menuDefaults.js` and `client/src/utils/menu.js`.
- Learn labs (lesson tasks with downloadable solutions): there are two labs in `server/learn-labs/<lab>/` (`base/` + `steps/NN/`, optional `lab.json` for title, zip prefix and readme): `claude-api-tool-use` (Angular AI Lab, steps 1-25, courses 2 and 3) and `genai-basics-lab` (key-free browser-only Angular app, steps 1-11, course 1). After changing any step file run `cd server && node scripts/buildLabZips.js <lab>` and commit the zips in `zips/`. Lesson code blocks are read from those same step files (`scripts/learn-ai/helpers.js`), so re-run `node scripts/seedAiCourses.js` after a change. Every lesson needs 1000+ words of explanation, one task and a download link.

The lab lessons (course 1, 2 and 3) point at the repo zips (`builtin`); admins can upload, replace or remove a zip on Admin > Learn > edit lesson (stored in `server/storage/learn-files/`, or `LEARN_FILES_DIR`; git-ignored, so never wipe it on deploy and back it up). nginx needs `client_max_body_size 30m;` for `/api/admin/learn/`. ## Country and language (i18n)
- A country dropdown (plus a language dropdown for countries with two, e.g. Canada en/fr, Morocco ar/fr) sits in a slim strip directly under the menu bar on the home page (rendered inside `Hero.jsx` after `NavBar`) (moved from the dashboard; `client/src/i18n/CountryBar.jsx`, `CountrySelect.jsx`). The choice is kept in `localStorage` (`prime_locale`) and applies to every page. Default is India / English, so public pages and what Google sees stay English. The server-rendered HTML, `<SEO />` titles and descriptions, canonical tags, JSON-LD and sitemap are NOT translated; `<html lang dir>` is set in the browser only.
- Countries and languages are in `i18n/countries.js` (en, es, fr, pt, ar; Arabic is right-to-left). All text lives in `i18n/dict/table.js` (resume, CV and app) and `i18n/dict/home.js` (home, features, ATS checker pages): rows `[English, es, fr, pt, ar]` plus `PATTERNS` for text with numbers or names. English text is the key; anything missing is shown in English. To add a phrase, add a row; to add a language, add a column, a `dict/<lang>.js` file (`build(col)`), and an entry in `LANGS`, `DICTS` (`engine.js`) and the countries.
- How it works: `I18nProvider` (in `main.jsx`) translates text nodes and `placeholder`, `title`, `aria-label`, `alt` attributes in the page and keeps watching React updates (exact-match lookup, so dynamic text only translates if it has a table row or pattern). Anything inside `data-no-i18n` is skipped; people's own text must sit in such a container (resume and CV previews already do), as must articles, job ads and inputs. Never put typed content outside it.
- Resume and CV labels are NOT translated by the page watcher but explicitly with `tr('Heading')` from `i18n/engine.js` (all 20 templates in `components/templates/`, `utils/cvModel.js` section headings, "Present", dates through `Intl` with the country locale). The CV PDF, Word file and copied text use the same `buildCvSections`, so they follow the language. Word gets right-to-left paragraphs for Arabic. The built-in PDF writer has no Arabic font, so for Arabic the CV "Download PDF" button opens the browser print window ("Save as PDF").
- Country guidance in that strip is only advice (photo, date of birth, marital status), never a rule; hints per country are in `countries.js` (`plain`, `common`, `follow`). Page sizes are not switched by country (resume Letter, CV A4).
- Not translated by design: articles and lesson bodies, blog, job ads, roadmaps' content, legal pages, admin, interview answers, anything user-written. Translated labels are longer, so outside English the home menu bar switches to the menu button below 1536px (`NavBar.jsx`). Layouts use `min-w-0`, `flex-wrap` and logical `start-`/`ms-` classes so they do not overflow in French, Spanish or Arabic; check new pages at 390px in `ar` and `fr`.
- Have a native speaker review Arabic, French, Portuguese and Spanish wording before relying on it for marketing pages.

## ATS "Apply fixes"
- Two entry points. (A) ATS checker page report: "Apply fixes to my resume" -> `POST /api/ats/reports/:id/apply` builds a NEW resume ("<file> (ATS fixed)") from the report's stored `sourceText` (private, `select:false`, never returned by any list/get) and opens it in the builder; the upload is never changed; repeat clicks reopen the same resume. Reports made before this feature have no text -> 409 `NO_SOURCE` ("upload again"). (B) Builder > ATS Score window: "Apply fixes to this resume" -> `POST /api/ats/apply-resume` returns proposed wording only (nothing saved); the builder applies it to the open resume with an Undo button, then normal Save/autosave.
- No-invention guards live in `server/utils/atsFix.js` (not just the prompt): numbers not in the source are dropped (a bullet line in A; the whole field reverts in B), skills must already appear in the resume, B can only change summary, descriptions and skills, never employers, titles, dates or contact details. Anything the AI cannot know goes in `needsYou`, shown in `AtsFixNotice.jsx` (builder banner, data from `sessionStorage ats_fix_<id>` for A). Dates are normalised to the builder's "YYYY-MM" (`toMonth`; year-only becomes January and is flagged).
- Both endpoints use the `ai_writing` paid-plan gate and `aiLimiter`; they do not use up an ATS check. The ATS page now says the text read from the file is saved for the owner. Test: /tmp/e2e/atsfix-test.mjs (mock AI in /tmp/ats/mockai.mjs answers with deliberately bad data).

## Performance (home page and app load)

While a page's code loads, the server-rendered HTML that was in `#root` stays on screen (`window.__ssrHtml`, captured in `main.jsx`), so no blank flash; later navigations show a small spinner.

## React rule: no early return before hooks
- Never `return` (or `return null`) above a `useEffect`/`useState`/other hook in a component. Hooks must run on every render. `PageNav.jsx` had this bug and white-screened /app -> /app/builder/:id when a resume was created from the dashboard. Compute a `hidden` flag, call all hooks, then `if (hidden) return null`.
- Email: transactional mail goes through Brevo's HTTPS API (`server/thirdPartyAPIs/userEmail.js`, built-in fetch, no package). Env: `BREVO_API_KEY`, `EMAIL_FROM` (must be a sender/domain verified in Brevo), optional `EMAIL_FROM_NAME`. SendGrid was removed. `notify`/contact alerts are best-effort and skip silently when the key is missing.
- Password reset: login screen (served at `/app`, no `/login` route) shows "Forgot password?" in login mode only. `POST /api/users/forgot-password` always returns the same message (no account enumeration), stores only a SHA-256 hash of the token (15 min), and emails the link via Brevo; `POST /api/users/reset-password/:token` needs 8-128 chars. Both pages are `noindex`.
